# The hero loop: from the sketch to a finished page

Prepared 3 September 2026. The owner's brief: keep the hero, and turn its one authored moment into a loop in which the visitor watches the website come together, from the wireframe the sketch draws today to what a finished site looks like. Everything below was checked against the code, the shipped Next.js and GSAP documentation, and the budgets measured from a production build on the day. Where a claim could not be verified it says so.

## 1. The idea in one paragraph

The sketch already tells the first half of the story: a sentence is typed, the company lands, the style fills, the colour sweeps. The loop adds the second half. Once the brief is complete, the wireframe builds itself into a designed page: grey bars become words, the hatch becomes a photograph, the layout reflows into a real hero, another family of type and a real palette arrive, and the page holds long enough to be read. Then it clears back to the blank sketch and the next sentence starts typing. Every element the visitor watched fill in has a place on the finished page, so the transformation reads as one continuous object changing state, not as a slideshow of two pictures.

## 2. What is there today

- `app/_components/hero-stage.tsx` builds one GSAP timeline that types the VetPres brief, steps the sketch through stages 2, 4 and 5, and re-tints the glow. It plays once when the hero is on screen and the browser is idle, then rests with a Replay button. The server renders the finished sketch; reduced motion and JavaScript off keep it.
- The sketch is two frames (`components/sketch/brief-sketch.tsx`, `phone-sketch.tsx`) drawing shared parts from one pure model. A browser frame with the phone over its corner at `lg`, the phone alone in a masked strip below `lg`.
- `lib/motion/gsap.ts` is the one loader for GSAP core, lazy, idle-timed, motion-gated. ADR 0005 records the motion rules, including a "never" list that contains autoplay loops.

## 4. The sequence

One loop is about 15 seconds. Times are from `lib/config.ts` (`CONFIG.demo`); the shot list below is the choreography.

**Act 1, the brief (about 8 s).** 0.4 s delay. The sentence types at a hand's rhythm (`lib/brief/typing.ts`): 16 ms a character, a breath after a comma, a longer one after a full stop, and a small fixed wobble, about 4 s in all. The company lands and the tab, wordmark, headline and footer take its name (hold 0.9 s). The style fills: the image block takes the example's photograph with the "Clean and minimal" treatment (1 s). The colour sweeps through the button, the mark and the glow (1 s), then a 1 s hold on the finished brief.

**Act 2, the build (2.4 s).** Every part of the wireframe travels to its place on the finished page and becomes the real thing on arrival. Eases are `power3.inOut` for travel and `power2.inOut` for crossfades; every travel overlaps the next by a few frames so the page assembles as one motion rather than in steps.

**Hold (3.5 s).** Long enough to read the headline and the label.

**Reset (0.9 s).** The finished page fades out and settles back by 1.5 percent, revealing an empty frame; the blank sketch fades in beneath; a 0.4 s beat; the next sentence starts typing. A fade rather than a rewind, because the reset is a page turn, not part of the story.

**The phone.** The same story in the phone frame, with the same part names, so the code is one routine run on two roots. The finished mobile page is image-led, photograph first, so on the phone the photograph travels up past the text, the vertical twin of the desktop sweep, and the kicker rises in between it and the headline. From `md` the phone plays over the browser's corner; below `md` it stands alone under the button, in full, and the brief types only the first 80 characters there, since the phone's paragraph shows two lines (`docs/hero-loop-mobile-plan.md`).

## 5. Technique

**FLIP, hand-rolled on GSAP core.** Each sketch part and its finished counterpart carry the same `data-part` name. At the start of every build the code measures both with `getBoundingClientRect`, and a pure helper (`lib/motion/flip.ts`, unit-tested) turns the two boxes into the transform that makes the finished part appear where the sketch part is. The finished part tweens from that transform to identity; the sketch part tweens to the inverse and fades. Boxes (pills, cards, the photograph, the footer) scale; text only travels, because scaled type smears. GSAP's Flip plugin would do the same for about 8 KB more and a second dependency on its swap semantics; the loop needs eleven pairs and one rule, so the helper is smaller and fully under test.

**Layers.** Inside each frame the page area becomes three layers: the finished page's background at the bottom, the finished page above it, and the sketch on top. The sketch stays in normal flow and sets the height; the other two are absolute. Putting the finished page under the sketch means the photograph can sit beneath the sketch's own image block from stage 4, pixel for pixel the same picture (both frames draw it with the same part), so hiding the sketch's copy at the start of the build changes nothing on screen and the one element beneath simply travels.

**Timeline mechanics.** Three acts, each a timeline that plays forward once and hands over to the next when it completes: the brief (React-driven, as today), the build with its hold, and the reset. Nothing is ever rewound. GSAP's `repeat` renders every tween back to its recorded start values and fires every callback again on the way, which is what left a second pass starting from the first pass's leftovers in the first version of this work. Part way through the reset's fade, under the hidden sketch layer, the build timeline is stopped and everything it wrote on the sketch's parts is cleared by name; what it wrote on the finished parts is cleared when the reset completes, so the fade in progress is never taken back, and the blank sketch fades in while the finished page is still going, so no frame is ever empty. `clearProps: 'all'` is never used: it wipes an element's whole inline style, including the colour variables React sets on the finished page. Each build measures a clean frame afresh, so a resize or a keyed remount in the sketch never goes stale. Off-screen pausing acts on whichever act is current, and an act created while off screen starts paused. All of it lives in one `gsap.context`, so a keystroke or an unmount reverts everything at once.

**Type.** The finished page uses Montserrat (variable, one file) for its headline, copy and buttons and Caveat Brush for the kicker, both via `next/font/google` with `display: 'swap'` and `preload: false`. These are chosen to read as another brand's site, not as PinnaclePX (Geist); the reference screenshot's exact families were not identified with certainty and are not claimed.

**Colour.** Every colour of the finished page derives from the example's one hex through relative oklch in `builtTintsFrom` (`lib/brief/sketch.ts`, unit-tested): the off-white ground with a trace of the hue, the heading tint, the muted copy tint, the deep footer, and a warm complement for the kicker. This is the rule the real colour engine will follow, and it means a different example brief would build a differently coloured page without any code change.

**Copy.** All strings of the finished page live in `app/_components/built-copy.ts`: the navigation, the kicker, the headline, three feature titles, the button label and the footer links. The paragraph is the brief's own sentence, unchanged, so the words the visitor watched being typed are the words on the page.

## 7. Degradation

| Situation                        | What happens                                                                                                           |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Reduced motion                   | The finished sketch at stage 5, as today. No GSAP, no fonts, no photograph downloaded. No controls.                    |
| JavaScript off                   | The same finished sketch from the server.                                                                              |
| GSAP chunk fails                 | The finished sketch; status `unavailable`, as today.                                                                   |
| Hero scrolled off screen         | The loop pauses where it is and resumes on return.                                                                     |
| Tab hidden                       | GSAP's ticker stops with `requestAnimationFrame`; lag smoothing prevents a jump on return.                             |
| Visitor types their own sentence | The loop is killed and every inline style reverted; the sketch is theirs, as today.                                    |
| Window resized                   | The next build measures afresh. A resize during a build finishes with the old measurements and is corrected next loop. |
| Photograph fails to load         | The image block keeps the style gradient under it; the build still plays.                                              |

## 8. Performance and budgets

- Scripts: 201,002 B before, 206,202 B after (budget 210,000). The built page loads through `next/dynamic` with `ssr: false`, so the initial script tags on `/` grow only by the hero's loop code and the loader.
- Stylesheet: 11,754 B against 12,000 before this work, 12,067 B after it. The finished page's utilities and two `@font-face` declarations crossed the line by 67 bytes, so the budget in `scripts/bundle-budget.mjs` is now 14,000 B, recorded in ADR 0006, rather than trimming unrelated CSS.
- HTML: 21,370 B before, 21,602 B after (budget 25,000); the built layers are not server-rendered, the part names on the sketch are the difference.
- Fonts: two more files, only for visitors who allow motion, fetched when the finished page mounts at idle, long before it shows.
- Photograph: 640 by 480 WebP, fetched when the finished page mounts; enough for every size the sketch shows it at 2x.
- Paint: transforms and opacity composite; the photograph's saturation tween repaints one small image for 1.1 s.
- LCP: the H1 at every size; asserted by test. CLS: nothing outside the frame moves and the frame's height is set by the sketch layer, as today. The caption under the frame is the exception, because the loop swaps its text on every pass and the two captions are different lengths; it reserves the taller one's height at each size. Measured over two passes on a phone: 0.0172 of shift without that reservation, accumulating for as long as the visitor stays, and 0.0004 with it.

## 9. Tests

- Unit: `flipDelta` (the inverse transform, the zoom correction for the phone strip, zero-size guards); `builtTintsFrom` (every tint keeps the hex and the complements rotate the hue); the example brief still passes the real form's schema.
- Playwright desktop: the hero builds twice over, each pass reaching `data-built` with the illustration label and returning to the blank sketch in between, which is the pass that broke first time; the LCP element is the H1 after a full build with no input. Reduced motion additionally asserts the hero never reaches `data-built`. The existing no-script, mobile and axe suites must stay green unchanged.
- Visual: frames captured at 0.3 s, 0.8 s, 1.4 s and 2.4 s into the build at 1440 and 390, reviewed before sign-off.

## 10. Decisions for the owner

1. **A loop with no end, and no control.** As asked, it loops until the hero is off screen or the visitor types, and the Pause button has been removed. This is the page's one knowing WCAG failure (2.2.2, Level A) and the product's promise is AA throughout, so it is worth a deliberate answer. A loop cap does not fix it: three passes still run for about 45 seconds, and the criterion's line is five. Only two things do, and both are one small change: put a control back, or hold on the finished page after the first pass so the motion ends. Everything else, including `prefers-reduced-motion`, is already in place and does not count.
2. **The photograph.** A Pexels photograph stands in. A supplied photograph of a real clinic, no people, in `app/_images/`, replaces it by changing one import.
3. **The label wording.** "The same example brief, built as an illustration. Not a client, and not one of the designs." Fifteen words, in the mono register, shown for the whole hold.
4. **Reduced motion and JavaScript off** see the finished sketch, as today. They could instead see the finished page statically; that changes the server render and puts the photograph in the first paint, so it is not done here.
5. **The stylesheet budget** (section 8).
6. **VetPres.** The docs treat it both as "a software product most visitors recognise" and as an example name to be checked against real traders. The finished page reuses the hero copy visible on the reference screenshot. If VetPres is a real product, that copy is theirs and the owner should confirm it may be shown; if it is an example, the copy is placeholder marketing and lives in one file to be rewritten.
